---

## 1. 이 단계가 하는 일

탭 잠금을 넣는다. 그런데 탭 잠금은 **배경을 두 번째 기록자로 만든다** — 탭이 닫히면
배경이 프로필의 잠금을 해제해야 하고, 그 순간 팝업과 배경이 서로 다른 실행 맥락에서
같은 저장소 키를 쓴다.

인수인계 §4.5 가 이 순서를 못 박았다: 큐가 먼저이고 탭 잠금이 그 위에 온다. 순서를
뒤집으면 오늘 이론인 델타 유실이 발현하는 결함이 된다.

그래서 이 단계는 **쓰기 경로를 하나로 만드는 일**이고, 탭 잠금은 그 위에 얹히는 첫
소비자다.

---

## 2. 범위

**포함:** 단일 기록자 전환 · 탭 잠금(획득 · 생명주기 · UI) · `activeTab` 도입 ·
`ruleCount` 분리 · 프로필 on/off 토글 · `empty-filter` 분할 · `useAppState` 테스트

**제외 — 2d 로:** JSON export/import · `filter.regex`/`pathPattern` 의 RE2 검증 ·
테마 토글과 ⋯ 메뉴

2d 를 가르는 기준은 성격이다. 이 단계는 **동시성**이고 2d 는 **신뢰 경계**(외부에서
들어온 입력의 검증)다. 인수인계 §5 가 "JSON import 가 regex·pathPattern 표면을 실제로
도달 가능하게 만든다"고 적었으므로 그 검증은 import 와 같은 단계에 있어야지 이 단계에
있을 이유가 없다.

## 3. 쓰기 아키텍처 — 배경이 유일한 기록자

### 3.1 결정

**팝업은 `chrome.storage` 에 쓰지 않는다.** 패치를 배경에 보내고, 배경이 직렬화된
큐 위에서 적용한다.

기록자가 하나이고 그 안에서 순차 실행되므로 델타 유실이 **좁아지는 게 아니라 사라진다.**
세대 번호 + 재시도는 `chrome.storage` 에 원자적 compare-and-swap 이 없어 확인과 쓰기
사이에 창이 남는다. 맥락 내 직렬화만으로는 팝업×배경 교차 경합이 남는다. 둘 다 부분해다.

설계 §6.1 이 `reconcile()` 을 단일 진입점으로 둔 이유가 "진입점이 하나라 상태 드리프트가
생길 자리가 없다"였다. 쓰기에 같은 원리를 적용하는 것이므로 새 발명이 아니라 확장이다.

### 3.2 형태

```
lib/storage/writer.ts     (배경 전용)
  enqueue(fn: (current: AppState) => Partial<AppState>): Promise<AppState>
    - 모듈 수준 프로미스 체인. 배경의 모든 쓰기가 여기를 지난다.
    - 팝업의 패치도, 탭 잠금 해제도, 같은 큐다.

lib/messaging/protocol.ts  (양쪽 공유)
  PatchRequest  = { type: 'patch'; delta: Partial<AppState> }
  PatchResponse = { ok: true; state: AppState } | { ok: false; error: string }
```

`patchState` 는 남되 **배경에서만** 호출된다. 순수성 가드와 같은 성격의 가드를 하나 둔다:
`entrypoints/popup/` 과 `components/` 에서 `lib/storage/state.ts` 의 쓰기 함수를
import 하지 않는다.

### 3.3 이 변경이 없애는 침묵과 새로 만드는 침묵

**없애는 것.** 오늘 `patch` 는 `void patchState(delta)` 다 — 쓰기가 거부되면 삼켜지고
낙관적 UI 는 틀린 값을 계속 보여준다. 왕복이 생기면 응답이 성공/실패를 실어오므로,
실패 시 낙관적 상태를 되돌리고 사용자에게 알릴 자리가 처음 생긴다. **이걸 하지 않으면
왕복만 추가하고 침묵은 그대로 두는 것이므로 같은 작업에 넣는다.**

**새로 만드는 것.** 메시지 왕복은 실패할 수 있는 새 표면이다. 두 경로를 명시적으로 다룬다:

| 상황 | 처리 |
|---|---|
| 서비스 워커가 잠들어 있음 | `sendMessage` 가 깨운다. 기동 경합으로 실패하면(`Could not establish connection`) 한 번 재시도한다. |
| 팝업이 왕복 중에 닫힘 | 쓰기는 배경이 소유하므로 그대로 착지한다. 응답 수신처만 사라진다 — 배경이 이 거부로 죽지 않아야 한다. |

둘 다 테스트로 못 박는다(§7).

### 3.4 낙관적 갱신은 유지한다

타이핑 응답성이 이 UI 의 요구사항이다(2b §5.3). `patch` 는 지금처럼 로컬 상태를 먼저
갱신하고, 배경의 응답이 `ok: false` 면 되돌린다. `stateItem.watch` 는 그대로 두어
배경이 스스로 쓴 변경(탭 잠금 해제)도 팝업에 전파된다.

### 3.5 세션 상태도 같은 울타리 안에

2b 리뷰가 `getSyncStatus` 에서 `onGrant` 와 같은 모양의 last-write-wins 를 찾았다.
`setSyncStatus` 도 배경만 호출한다 — 이미 사실상 그렇지만 강제되지 않았다. 같은 가드로
강제한다.

## 4. 탭 잠금

### 4.1 무엇에 묶이는가

**`tabId` 에만 묶는다.** 잠근 탭이 다른 사이트로 이동해도 잠금은 유지되고, 어디에
적용되는지는 도메인 필터가 정한다. 잠금 시점 origin 을 함께 기록해 이동 시 적용을
멈추는 안은 채택하지 않았다 — SPA 라우팅과 리다이렉트에서 잡음이 되고, "이 탭"이라는
사용자의 기대와 어긋난다.

`priority.ts:36` 이 이미 잠긴 프로필을 높게 정렬한다. 한 탭에 두 프로필을 잠그는 것을
막지 않는다 — 우선순위가 이미 순서를 정한다.

### 4.2 권한 — `activeTab`

`chrome.tabs.query` 는 `title`·`url` 을 아무에게나 주지 않는다. `tabs` 권한이나 그 탭에
대한 host 권한이 있어야 채워진다. **`tabs` 권한은 설치 경고를 만든다** — 이 프로젝트가
지켜온 "설치 시 경고 0개"를 깨고, 멀웨어로 내려간 도구의 대체품이라는 존재 이유와
직접 충돌한다.

`activeTab` 은 사용자가 확장을 클릭한 순간의 탭에만 임시 접근을 주며 **설치 경고를
만들지 않는다.** Phase 2a 가 계획에 있던 `activeTab` 을 일부러 넣지 않은 이유가
"소비자가 없는데 넣으면 매니페스트 테스트의 단언이 형식만 남고 내용은 거짓이 된다"였다.
탭 잠금이 첫 소비자다.

**이 결정은 실측으로 검증한다.** 구현 첫 작업이 스파이크다:

- `activeTab` 만으로 팝업에서 `tabs.query({active:true, currentWindow:true})` 의
  `title` 이 실제로 채워지는가
- 배경도 같은 접근을 갖는가, 아니면 팝업이 읽어 배경에 넘겨야 하는가
- `chrome://` 페이지처럼 확장이 접근할 수 없는 탭에서 무엇이 오는가
- 팝업이 닫힌 뒤 `activeTab` 이 만료되면 `tabs.get(id)` 이 무엇을 돌려주는가 —
  §4.3 의 생존 확인이 이것에 의존한다

스파이크 결과가 설계와 다르면 설계를 고친다. 이 프로젝트에서 실측이 설계를 뒤집은 것이
이번이 세 번째가 된다(권한 사다리 4단→6단, MV3 CSP 와 인라인 스크립트).

### 4.3 생명주기

설계 §6.3 을 그대로 구현한다.

```
SW 기동
  → 상태 읽기
  → 잠금 프로필마다 tabs.get(id)
      ├ 살아있음 → 세션 룰 재등록
      └ 사라짐   → 잠금 해제 + tab-lock-stale
  → reconcile()
```

`tabs.onRemoved` 를 `reconcile()` 트리거에 추가한다 — 설계 §6.1 의 표에 있으나
`entrypoints/background.ts` 에 아직 배선되지 않았다.

**해제는 배경의 쓰기이므로 §3 의 큐를 지난다.** 이것이 큐가 먼저여야 하는 이유다.

### 4.4 UI — 필터 블록 안

잠금 컨트롤은 도메인·리소스 타입 옆에 둔다. 잠금은 실제로 필터다 — `compile` 이 적용
범위를 정하는 데 쓰고, "어디에 적용되는가"의 답이 한 자리에 모인다.

프로필 편집 스트립에 두지 않는다. 그 스트립은 활성 탭을 다시 클릭해야 열리므로 **켜둔
잠금이 평소에 보이지 않는다** — 적용 범위를 조용히 좁히는 상태가 화면에 없는 것은 이
프로젝트가 없애온 부류의 침묵이다.

표시:

| 상태 | 보이는 것 |
|---|---|
| 꺼짐 | "이 탭에만 적용" 토글 |
| 켜짐 | 토글 + 잠긴 탭 제목. 제목을 못 읽었으면 탭 번호로 대체 |
| 잠긴 탭이 사라짐 | `tab-lock-stale` 진단이 띠에 뜨고 토글은 꺼진 상태로 돌아간다 |

## 5. 함께 닫는 것

이 넷은 §3·§4 가 건드리는 자리에 이미 있거나, 2b 가 명시적으로 여기로 넘긴 것이다.

### 5.1 프로필 on/off 토글

모델에 `enabled` 가 있고 `compile.ts:28` 이 읽지만 **UI 경로가 없다.** 2b 는 이 때문에
두 결함을 "도달 불가"로 분류해 닫았다(카운트와 탭 표식). 토글이 생기면 둘 다 살아난다 —
이미 고쳐 두었으므로 이 단계에서는 **토글을 붙이고 회귀 테스트가 여전히 초록인지**
확인하는 일이다.

토글은 프로필 편집 스트립에 둔다(이름·색·삭제 옆 — 프로필 메타데이터다). 그리고 2b
리뷰의 M3 를 여기서 닫는다: 꺼진 프로필의 "0 of N" 에 이유를 붙인다.

### 5.2 `empty-filter` 분할

한 종류가 정반대 두 상태를 덮고 있다(인수인계 §4.3):

| 상태 | 결과 | 분할 후 |
|---|---|---|
| 도메인 목록이 비어 있음 | 룰이 등록되고 **모든 사이트**에 매칭 | `empty-filter` / warning |
| 도메인이 전부 무효 | 룰이 **아예 없음** | `no-usable-domain` / **error** |

`DiagnosticKind` 가 10 → 11 이 된다.

**분할과 동시에 2b 의 표시 층 우회를 되돌린다.** `profileMarker` 는 억제를 신호로 받아
error 표식을 붙이는데(2b I3), 분할 후에는 `no-usable-domain` 이 error 라 severity 규칙이
스스로 잡는다. 되돌리지 않으면 같은 판단이 두 자리에 남는다 — Phase 2a 에서 가장 비쌌던
결함의 형태다.

되돌릴 때 `grid.test.ts` 의 "진단이 0건인 억제 프로필" 케이스를 함께 판단한다. 2b 의
N2 수정 이후 그 케이스의 유일한 실현자(꺼진 프로필)가 사라졌으므로, 우회와 함께 나가야 한다.

### 5.3 `ruleCount` 분리

`SyncStatus.ruleCount` 는 dynamic + session 합산이다. 탭 잠금이 생기면 사용자가 알아야
할 것이 둘로 갈린다:

```ts
interface SyncStatus {
  lastError: string | null;
  ruleCount: { always: number; tabLocked: number };   // was: number
}
```

세션 저장소의 형태를 바꾸는 변경이라 UI 를 쓰기 전에 한다. `StatusFoot` 이
"항상 켜짐 N · 탭 고정 M" 을 보인다.

### 5.4 `useAppState` 테스트

인수인계 §4.5 가 지적한 공백이다. `state.test.ts` 는 모듈 수준만 못 박고 훅 수준
정확성은 아무것도 보장되지 않는데, 2b 가 이 훅 위에 그리드 전체를 올렸다. §3 이 이 훅을
바꾸므로 여기서 메운다.

## 7. 테스트

3층 구조를 유지한다(설계 §9.4).

**순수 층** — `writer.ts` 의 큐는 저장소를 주입받아 브라우저 없이 테스트한다. 동시
호출 N 개가 전부 반영되는지, 순서가 보존되는지, 하나가 던져도 뒤가 계속되는지.

**어댑터 층** — 메시지 왕복. `@webext-core/fake-browser` 는 `runtime.sendMessage` 를
던지는 스텁으로 두므로 손으로 심은 스파이로 테스트한다(2a 가 DNR·permissions 에서 쓴
방식과 같다). 반드시 덮을 두 경로:

- 서비스 워커 기동 경합 → 재시도 후 성공
- 팝업이 왕복 중 닫힘 → 쓰기는 착지하고 배경은 죽지 않는다

**E2E** — 탭 잠금이 실제로 탭을 가르는지. 잠근 탭에서는 헤더가 바뀌고 **다른 탭에서는
바뀌지 않는** 것을 에코 서버로 확인한다. 이 단계에서 이것 하나가 다른 모든 단언보다
무겁다 — 나머지는 전부 이 동작이 맞다는 전제 위에 있다.

**회귀** — 2b 가 "도달 불가"로 분류해 닫은 두 결함(§5.1)이 토글 도입 후에도 초록인지.

## 8. 하지 않는 것

- **JSON export/import 와 RE2 검증** → 2d. 성격이 다르다(§2)
- **테마 토글** → 2d
- **잠금 시점 origin 기록** → §4.1 에서 기각
- **탭 잠금의 창(window) 단위 확장** → v1 범위에 없다
- **`Diagnostic` 의 포함/제외 도메인 구분**(인수인계 §4.6) → 제외 도메인 UI 가 생길 때

## 9. 알려진 제약

- **`activeTab` 은 팝업이 열린 순간의 탭에만 유효하다.** 잠금 후 제목이 바뀌어도
  갱신되지 않는다. 저장된 제목은 "잠글 때 그 탭이 무엇이었는지"의 기록이지 현재 상태가
  아니다 — UI 문구가 이를 주장하지 않아야 한다.
- **세션 룰은 SW 가 죽으면 사라진다.** 재구축이 정상 경로이고(§4.3), 그 사이 짧은 창에서
  잠긴 프로필의 헤더가 적용되지 않는다.
- **`patchState` 의 top-level 병합은 그대로다.** `profiles` 배열 내부의 동시 편집은 큐가
  순서를 보장하므로 유실되지 않지만, 두 기록자가 같은 프로필의 다른 필드를 동시에
  고치면 나중 것이 이긴다. 오늘 그런 호출부는 없다.
- **한 프로필 안 두 행이 같은 헤더를 건드리면 행마다 `profile-conflict` 이 뜬다**
  (인수인계 §4.6). 이 단계가 바꾸지 않는다.
