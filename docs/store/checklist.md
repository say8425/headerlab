# Chrome Web Store — submission checklist

Run top to bottom. Steps 1 and 2 are account work that has nothing to do with
this repository and can be done while everything else waits; step 3 onward is
the listing itself.

Everything to paste lives beside this file:

| File | Covers |
| --- | --- |
| `listing.md` | Store listing tab — category, URLs, assets, which fields come from the manifest |
| `description.<locale>.md` | The detailed description, one per language |
| `privacy.md` | Privacy practices tab — single purpose, permissions, data use |
| `../../PRIVACY.md` | The privacy policy itself, the URL you submit |
| `assets/` | Every image, generated by `pnpm store:assets` |

---

## 1. Developer account

- [ ] Register at <https://chrome.google.com/webstore/devconsole> and pay the
      one-time registration fee. The console states the current amount — do not
      budget from this file.
- [ ] **Choose the account email carefully. It cannot be changed afterwards**,
      and a deleted account's email can never be reused. Google's own advice is
      to use an address created for publishing rather than a personal one.
- [ ] Verify the contact email. An unverified one blocks publishing.
- [ ] Set the publisher display name. It appears on the listing beside the item.

### Trader / non-trader

**Decided: non-trader** (owner, 2026-08-21).

- [ ] Declare **non-trader** in the developer account.

The EU's Digital Services Act obliges the store to identify and verify traders.
A trader acts "for purposes relating to their trade, business, craft or
profession"; a non-trader acts outside it. Google is explicit that the developer
self-declares and that it cannot make the determination for anyone.

**What declaring non-trader means, and what it does not:**

- Consumers are told that consumer rights arising from consumer-protection law
  do not apply to contracts between them and you. For a free, unmonetised
  extension under Apache-2.0 there is no such contract to begin with.
- **It does not restrict where the item can be distributed.** Nothing in the
  policy ties the declaration to a region, so the Distribution tab's "All
  regions" below stands. Checked, because the two settings would otherwise
  contradict each other in this same file.
- The trader route is what publishes a verified address and an SMS-confirmed
  phone number on the listing. That does not apply here.

**Not established, so do not assume either way:** what contact details the store
publishes for a *non*-trader. The policy pages describe only the trader case,
and this has not been measured. The account's contact email is verified
regardless — see the step above it — but whether that email is shown on the
listing is a question the dashboard will answer at declaration time.

**Revisit if the circumstances change**, not the extension: the status is a fact
about the publisher, so it can change without a line of code moving — if the
item ever becomes paid, or comes to be published in the course of a profession.

## 2. Prepare the package

- [ ] `pnpm check:all` — typecheck, lint, format, unit tests, package tests.
- [ ] `pnpm test:e2e` — the suite that drives a real browser.
- [ ] `pnpm zip` → `.output/headerlab-<version>-chrome.zip`. **Clear the old ones
      first** — `wxt zip` does not remove them, and the two checks below name the
      archive rather than glob for it precisely because a leftover wins:

      ```bash
      rm -f .output/*.zip && pnpm zip
      ZIP=".output/headerlab-$(node -p "require('./package.json').version")-chrome.zip"
      ```

      Both commands below use `$ZIP`. Do not replace it with
      `.output/headerlab-*-chrome.zip`: with two archives present the shell
      expands that in sorted order and `unzip` reads the *first* argument, so a
      stale build answers and the answer looks right. Measured on 2026-08-23,
      with `1.3.1` left over beside a fresh `1.5.0`, the glob printed the
      manifest of `1.3.1`.

- [ ] Confirm the zip carries all five locales, or the listing cannot be written
      in five languages:

      ```bash
      unzip -l "$ZIP" | grep messages.json
      ```

      Five lines: `en`, `es`, `ja`, `ko`, `zh_CN`.

- [ ] Confirm the manifest inside the zip still declares exactly two install-time
      permissions and no `host_permissions`:

      ```bash
      unzip -p "$ZIP" manifest.json
      ```

      `permissions` must be `["storage", "declarativeNetRequestWithHostAccess"]`
      and there must be no `host_permissions` key at all. `tests/unit/manifest.test.ts`
      asserts this, so a green `pnpm check` already proves it — the command is
      here because this is the one claim the whole listing rests on.

## 3. Prepare the assets

- [ ] `pnpm store:assets` → 28 images in `docs/store/assets/`.
- [ ] Look at them. The generator checks every file's pixel dimensions and
      refuses anything the store would reject, but it cannot see a missing CJK
      font: on a machine without Korean, Japanese and Chinese faces installed the
      captions render as empty boxes and every automated check still passes.

## 4. Upload

- [ ] Dashboard → **Add new item** → upload the zip.
- [ ] Let the manifest validation pass before filling anything in. A rejected
      package makes the rest of the form moot.

## 5. Store listing tab

Work through `listing.md`. In short:

- [ ] Category: **Developer Tools**.
- [ ] Default language: **English**.
- [ ] Detailed description, English — from `description.en.md`. **Paste as plain
      text**; the store renders no Markdown.
- [ ] Store icon: `assets/store-icon-128.png`. **Not** `public/icon/active-128.png`
      — the store wants 16px of transparent padding the toolbar icon does not have.
- [ ] Screenshots, English: the five `*.en.png` files, in the numeric order their
      names carry.
- [ ] Small promo tile: `assets/promo-small-440x280.png`. Not optional in
      practice — an item without one ranks lower in store search.
- [ ] Marquee tile: `assets/promo-marquee-1400x560.png`.
- [ ] Official / Homepage URL: `https://github.com/say8425/headerlab`.
- [ ] Support URL: `https://github.com/say8425/headerlab/issues`.
- [ ] Mature content: **No**.

Then, for each of `ko`, `ja`, `zh_CN`, `es`:

- [ ] Switch the language dropdown at the top of the tab.
- [ ] Paste that locale's detailed description.
- [ ] Upload that locale's five screenshots.

The dropdown offers only the locales the uploaded package declares, which is why
step 2 checks for them. The two promo tiles are **not** localisable — the store
says so outright — so they are uploaded once and shared.

## 8. Submit

- [ ] Consider **deferred publishing** — publish manually after the review
      passes rather than automatically. You then have up to 30 days to publish,
      which is useful if you want the README updated in the same breath.
- [ ] Submit for review.

Expect this one to take longer than a trivial extension. It requests a broad
host permission (optionally) and native messaging (optionally), and both draw
attention. The justifications in `privacy.md` are written for exactly that
reader.

## 9. After it is published

None of this blocks the submission, but all of it is wrong until it is done.

- [ ] `README.md` says "There is no Chrome Web Store listing." Replace it with
      the install link.
- [ ] The same sentence exists in all four translations —
      `docs/README.{ko,ja,zh,es}.md`.
- [ ] Add a store badge if you want one.
- [ ] `packages/headerlab/README.md` and `packages/plugin/`'s skill text mention
      installing the extension; check whether they should now point at the store.

---

## Things that will not happen, so do not wait for them

- **There is no Chrome Web Store step in CI.** `release-please.yml` builds the
  zip and attaches it to the GitHub release; it does not submit anything. Adding
  a `wxt submit` step needs four secrets that do not exist. Add it with the
  listing, not before.
- **A release PR opened by the default `GITHUB_TOKEN` runs no checks.** That is
  GitHub's loop-prevention rule, not a misconfiguration.
- **The store will not tell you the item name is wrong.** The title and the
  summary come from the manifest, so fixing either means shipping a new package,
  not editing the listing.
